 背景是 CAS 雷达检测接口耗时 30-120 秒，用 RabbitMQ 做异步处理。但 RabbitMQ 在网络抖动时会重复投递，加上消费者崩溃恢复后也会重新消费，如果不处理好就会出现：
  - 同一个任务被扣两次点数
  - 同一个任务生成两份检测记录

  我的解决方案是三层保护：

  1. 状态机原子更新：消费者拿到消息后，用 UPDATE WHERE status=0 条件更新为「处理中」，MySQL 的 affected_rows=0 就说明已经被其他人拿走了，直接 ACK 退出。
  2. consumer_num 计数：每次重试 consumer_num + 1，超过 3 次就标记为失败不再重试，避免死循环。
  3. 点数 Lua 扣费：扣点数用 Redis Lua 脚本保证原子性，即使 Consumer 逻辑有 bug 重复执行，也只会扣一次。

  再加上 request_id 全链路透传到日志和 DB，出问题时 Kibana 一查就能定位到具体哪一环失败。」

  Q：协程和异步队列的区别？

  A：「协程解决的是单个请求内多个 IO 并行的问题，比如一个检测要调 3 个 API，用 Parallel 并发跑把 10 秒降到 5 秒，但整体还是同步响应用户。

  异步队列解决的是请求和处理解耦的问题，用户发起请求立即返回 task_id，真正的计算在后台慢慢跑，30 秒都不嫌慢，用户通过 task_id 轮询结果。

  我们项目里这两个是组合使用的：同步 API 里用协程并行调用保证响应快；重度计算任务投递到 RabbitMQ，消费者内部也用协程并发处理多个子任务，双重并行。」

Redis的LUA 核心保证： ▎ Redis 是单线程执行命令的，Lua 脚本在 Redis 内部作为一个整体原子执行，期间不会被任何其他客户端的命令插入。
关键性质：
  1. 原子性 — 脚本执行期间其他命令全部排队等待
  2. 隔离性 — 脚本看到的数据是自己启动那一刻的快照，其他客户端的修改进不来
  3. 高性能 — 多条命令打包一次 RTT，内部调用无网络开销

  副作用： 脚本不能执行太久（Redis 单线程会被阻塞）！默认 lua-time-limit 5 秒，超时后只能 SCRIPT KILL 或重启

  const LUA_DEDUCT = <<<'LUA'
  local key = KEYS[1]
  local deduct = tonumber(ARGV[1])
  local current = tonumber(redis.call('GET', key) or 0)

  if current < deduct then
      return -1
  end

  redis.call('DECRBY', key, deduct)
  return current - deduct
  LUA;





Q：RabbitMQ 消息确认机制

  A：「RabbitMQ 消费者处理完消息后有三种响应：

  - ACK：告诉 MQ 处理成功，消息从队列永久删除。最常用，处理成功或确定不需要重试时用。
  - REQUEUE：重新入队，让自己或其他消费者再消费一次。适合临时性错误，比如网络抖动、DB 连接断开。但要配合重试计数，否则会死循环——我一般用 Redis 存重试次数，超过 3 次就改走死信队列。
  - NACK（requeue=false）：拒绝消息，如果队列配了 x-dead-letter-exchange 就进死信队列，否则直接丢弃。适合参数非法、业务规则拒绝这种重试也没用的错误，但又不想直接丢失消息，便于人工排查。

  死信队列我会配一个独立消费者，把失败消息写到 failed_messages 表 + 告警钉钉，运维可以看到所有失败的业务然后人工修数据或重放。」

  Q：REQUEUE 会不会导致消息顺序乱？

  A：「会。REQUEUE 是把消息放回队列头部（不同 MQ 版本略有差异），如果业务严格要求消息顺序（比如订单状态流转），REQUEUE 会打乱顺序，应该改成 ACK + 投递到延迟队列重试，保持原队列的顺序。」
